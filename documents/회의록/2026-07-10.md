## 핵심 논의

| 주제 | 당시 논의 |
|---|---|
| 공시 | 원문을 보존하고, 8-K·10-Q·Form 4처럼 성격이 다른 공시를 코드로 분류한 뒤 필요한 값만 전략가 전달 JSON에 포함 |
| 하드블록 | 상장폐지·거래정지 등 위험 사건은 LLM 해석 전에 코드가 차단하는 방향 |
| 공시 점수 | `importance`, `sentiment_score`, `risk_score`처럼 의미가 다른 값을 구분해 전달·검증 |
| 뉴스 | 원문/수집 정보와 전략가가 읽는 집계 신호를 구분하고, 여러 기사에 대한 종합 요약을 사용 |
| 대표기사 | 단일 대표기사 선택은 혼선이 있어, 최종 설계에서는 원문 근거와 집계 신호의 역할을 분리 |
| 시각 필드 | 공시 제출 시각, 수집·생성 시각, 분석 기준일의 의미가 겹치는지 검토하고 필드 정의를 다시 맞추기로 함 |
| 문서화 | 컬럼별 설명을 여러 페이지로 흩기보다 팀이 함께 보는 표와 예시를 기준으로 정리하기로 함 |

## 후속 반영

이 회의의 문제 제기는 이후 2차 설계에서 다음 구조로 정리됐다.

- 원본 수집 원장과 전략가 전달용 집계 신호를 분리
- 공시·뉴스의 출처와 사건 유형을 원장에 보존
- 수치·분류·하드룰은 코드가 계산하고, LLM은 해석이 필요한 부분만 담당
- 모든 판단은 근거 행을 FK로 연결해 나중에 역추적 가능하게 함

상세한 최종 결과는 [최종 프로젝트 한눈에](../facts/최종프로젝트.md)를 참조한다.
